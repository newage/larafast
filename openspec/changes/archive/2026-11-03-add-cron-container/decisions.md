# Журнал рішень: окремий cron-контейнер у docker

## Проблема
`schedule:run` ніхто не запускає: у docker немає процесу, який щохвилини викликає планувальник Laravel (у `routes/console.php` вже є `cloudflare:refresh-ips`). Без цього заплановані команди на проді не виконуються. Для local і prod потрібні різні розклади.

## Дано
- Сервіси compose: php (fpm), nginx, mysql, node; cron-сервісу немає — перевірено: `docker/docker-compose.yml`.
- `docker/crond/` порожня (заготовка під файли розкладу) — перевірено: `ls docker/crond`.
- `APP_ENV` береться з кореневого `.env` через `make` (`--env-file ../.env`), у compose доступний як `${APP_ENV:-local}` — перевірено: `docker/Makefile`, `docker/docker-compose.yml`.
- Образ php: `php:8.5-fpm`, користувач `app`, xdebug лише при `APP_ENV=local` — перевірено: `docker/php/Dockerfile`.
- Для prod: `*/5 * * * * php artisan schedule:run` — зі слів розробника (`.agents/propose/add-cron.md`).
- Домен: інфраструктура (docker), без змін у коді застосунку.

## Концепт рішення
**Обрано:** окремий сервіс `cron` у compose, зібраний з того ж `docker/php/Dockerfile`; розклад — нативні crontab-файли `docker/crond/prod` і `docker/crond/local`; файл обирається за `APP_ENV`; виконує supercronic.
**Чий:** запропонував розробник (окремий контейнер, 2 файли за оточенням); формат і рантайм — згенеровано у воронці.
**Чому:** нативний crontab не потребує конвертера, supercronic читає його як є, бачить змінні контейнера, працює від `app` і пише лог у stdout.
**Відкинуто:**
- JSON + генерація crontab — додає скрипт-конвертер і точку поломки; корисні поля (`description`, `enabled`) покриваються коментарями.
- Debian `cron` — root, змінні оточення треба прокидати вручну, лог не потрапляє в `docker logs`.
**ADR:** ні — легко оборотне, інфраструктурна конфігурація без перетину контекстів.

## Вектор
```
.env (APP_ENV) ─► make ─► docker compose
                           └─ сервіс cron (образ php + supercronic)
                                └─ supercronic docker/crond/${APP_ENV:-local}
                                     └─ php artisan schedule:run ─► routes/console.php
```
- Файли розкладу монтуються через наявний том `..:/var/www/larafast`, окремого копіювання в образ немає.
- Вибір файла — у `command` сервісу через `${APP_ENV:-local}`; ніякої логіки в скриптах.
- supercronic додається в `docker/php/Dockerfile`, образ спільний з php (один образ — менше збірок).
- Застосунок не змінюється; `schedule:run` лишається єдиною точкою входу в розклад Laravel.

## Деталі
### Формат файлів розкладу
**Рішення:** нативний crontab.
**Чому:** конвертер не потрібен, коментарі замінюють описові поля.
**Альтернатива:** JSON + генерація — відкинуто, див. вище.
**ADR:** ні — можна замінити, не чіпаючи застосунок.

### Рантайм cron
**Рішення:** supercronic.
**Чому:** нативно читає crontab, передає змінні, пише лог у stdout, працює не від root.
**Альтернатива:** Debian `cron` — відкинуто, див. вище.
**ADR:** ні — замінюється одним рядком у Dockerfile і compose.

## Відкриті питання
- Версія і спосіб завантаження supercronic (фіксована версія + перевірка контрольної суми) — вирішується в `propose`/реалізації, не змінює концепт.

## Припущення
- `docker/crond/local` містить `* * * * * php artisan schedule:run` (стандартний інтервал Laravel для розробки) — розробник не назвав вміст local; не блокує, легко змінити.
- Образ збирається з тим самим `APP_ENV`, що й php (xdebug у cron-контейнері лише для local); окремого target не вводимо.
- cron-сервіс залежить від `mysql` (`depends_on`), як і php.
- Робоча директорія і користувач cron-сервісу — `/var/www/larafast` і `app`, як у php-образі.
